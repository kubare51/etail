1. Entity Configuration (config.json)

Each importable entity (Customer, Employee, Account, etc.) is defined by a JSON config file stored at:

api/application/config/migration/{entity_name}.json

1.1 Complete JSON Schema

{
  "entity": "customer",                          // Entity identifier

  "ai": {                                        // [OPTIONAL] AI column matching
    "enabled": true,                             //   Enable/disable AI suggestions
    "max_rows": 20                               //   Max rows sent to AI for analysis
  },

  "validation": {
    "required_file_name_pattern": "customer*.xlsx",  // File name pattern check
    "required_sheet_name": "port_customer"            // Required Excel sheet name
  },

  "migrations": [{
    "destination_table": "customer",              // Target DB table name
    "primary_key": "id_customer",                 // Primary key column

    "mappings": {                                 // Column mappings (see §1.2)
      "db_column_name": { ... }
    },

    "children": [{                                // [OPTIONAL] Child tables
      "destination_table": "address",
      "foreign_key": "id_customer",               // Links to parent's primary_key
      "mappings": { ... }
    }]
  }],

  "report": [{                                    // [OPTIONAL] Post-import report queries
    "aggregation": "count",
    "field": "mobile",
    "group_by": ["customer.id_branch"],
    "select": "SQL SELECT clause",
    "primary_key": "id_customer",
    "where": { "current_import": { "added_by": 6 } },
    "left_join": { "table": "branch", "on": "branch.id_branch = customer.id_branch" }
  }]
}

1.2 Column Mapping Types

Type A: Direct Column (Excel → DB)

"firstname": {
  "source_column": "first_name",         // Excel column header (case-insensitive)
  "validations": {
    "type": "string",                    // string | numeric | date | email | time
    "max_length": 50,                    // Max character length
    "required": true                     // Is this column mandatory?
  }
}

Type B: Lookup Column (Excel name → DB ID)

"id_village": {
  "lookup": {
    "table": "village",                  // Lookup table in DB
    "source_column": "area_name",        // Excel column to read
    "match_column": "village_name",      // DB column to match against
    "return_column": "id_village",       // DB column to return (usually ID)
    "create_if_missing": true,           // Auto-INSERT if not found
    "check_if_have": false               // Just verify exists, don't return value
  },
  "validations": { "type": "string", "max_length": 100, "required": false }
}

Type C: Duplicate Check Column

"mobile": {
  "source_column": "mobile",
  "validations": { "type": "numeric", "length": 10, "required": true },
  "check_if_exists": true                // Skip row if this value already exists in DB
}

1.5 Report Configuration

The report array defines post-import summary queries. Each entry generates one report table on the Report page.

FieldDescriptionExample
aggregationAggregation type"count"
fieldColumn to aggregate"mobile"
group_byGROUP BY columns (array)["customer.id_branch"]
selectFull SELECT clause (raw SQL)See examples below
primary_keyPrimary key for MAX() tracking"id_customer"
where.current_importFilter for "current import" rows{ "added_by": 6 }
left_joinOptional JOIN for labels{ "table": "branch", "on": "..." }
Important: The select clause MUST include max({primary_key}) as last_id — this is used internally to distinguish "before import" vs "current import" rows.
⚠️ Critical (v2.1): The destination table's primary_key column MUST have AUTO_INCREMENT set in the database. Without it, imported rows will get id = 0, the "Current Import" report will show 0, and subsequent imports will fail with Duplicate entry '0' for key 'PRIMARY'. Verify with: 
SHOW CREATE TABLE customer;  -- Check for auto_increment
ALTER TABLE customer MODIFY id_customer INT AUTO_INCREMENT;

Report SELECT Example (with JOIN)

"select": "IFNULL(branch.name, '-') as branch, count(customer.mobile) as count, max(customer.id_customer) as last_id",
"left_join": { "table": "branch", "on": "branch.id_branch = customer.id_branch" }

Report SELECT Example (with CASE expression)

"select": "count(mobile) as count, max(id_customer) as last_id, if(added_by=6,'Import','Other') as source"

2. Creating a New Entity Config

Step-by-Step Guide

Step 1: Identify the target tables

Determine the main database table and any child tables. Example:

  • Main: customer (primary key: id_customer)
  • Child: address (foreign key: id_customer)

Step 2: Map Excel columns to DB columns

For each column in the Excel template:

  1. Decide the DB column name it maps to
  2. Decide if it's direct, lookup, or duplicate-check
  3. Define validation rules (type, length, required)

Step 3: Create the JSON file

// Save as: api/application/config/migration/newentity.json

{
  "entity": "newentity",
  "validation": {
    "required_file_name_pattern": "newentity*.xlsx",
    "required_sheet_name": "port_newentity"
  },
  "migrations": [{
    "destination_table": "your_table",
    "primary_key": "id_your_table",
    "mappings": {
      // Add your column mappings here
    }
  }]
}

Step 4: Download Template for Testing

With PortMax v2.1, you don't need to manually create a test Excel file. Instead:

  1. Select the entity in the UI (searchable dropdown)
  2. Click "📥 Download Template" to generate an Excel file with correct headers + validation rules row
  3. Fill in test data rows and upload
  4. Validate and check for any mapping errors
  5. Import and verify data in the database
⚠️ Caution: Always test with a small dataset first. The config is case-insensitive for column matching, but the Excel sheet name must match exactly.

4. Backend Configuration

4.1 Global Config (global_configs.php)

File: global_configs.php (project root)

class Globals {
    public static $hostname = "localhost";
    public static $username = "root";
    public static $password = "";
    public static $database = "etail_v3";           // Default DB (used for login)
    public static $timezone = "Asia/Kolkata";
}
Note: These are default DB credentials for the client's application database. The login authentication itself uses rest_valid_logins (see §4.2a below).

4.2a Login Authentication (rest.php)

File: api/application/config/rest.php

Login credentials are configured in the rest_valid_logins array. The login form validates username and password against this config (not the database).

// api/application/config/rest.php (line ~252)
$config['rest_valid_logins'] = array('portmax' => 'Lmx#2026@port');

To change login credentials:

  1. Open api/application/config/rest.php
  2. Find rest_valid_logins array
  3. Change the key (username) and value (password)
  4. Multiple logins can be added: array('user1' => 'pass1', 'user2' => 'pass2')
Security: Passwords are stored in plain text in this config file. Ensure this file is not publicly accessible via .htaccess rules.

7. Adding a New Client Deployment

Step 1: Set up the database

Ensure the client's database has the required lookup tables (city, state, country, village, branch, etc.) populated with data.

Step 2: Create entity config files

Create JSON config files for each entity the client needs to import. Place them in api/application/config/migration/.

Step 3: Set login credentials

Update api/application/config/rest.php → set rest_valid_logins username and password for the client.

Step 4: Update global_configs.php

Set the database credentials for the client's server.

Step 5: Update config.js

Update the API URL to point to the client's server domain.

Step 5: Build and deploy

cd migration && npm run build
# Copy entire project to client server

Step 6: Verify

  1. Login with client credentials
  2. Upload a small test file
  3. Validate → Backup → Import → View Report
  4. Verify data in database
