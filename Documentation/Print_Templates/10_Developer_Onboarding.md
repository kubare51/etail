# Developer Onboarding / How to Work on This Module

## Setup steps to run this feature locally

1. **Standard eTail local setup** — this module has no special environment requirements beyond the rest of the admin app. It doesn't use `.env` files, and `admin/application/config/config.php` has no print-template-specific entries at all.
2. **Database**: local DB credentials are hardcoded in `admin/application/config/database.php` (`hostname=localhost, username=root, password="", database=retail_dev2` by default) — the production `Globals` class path is bypassed locally, so you don't need to set that up. Ensure your local DB has the `print_templates`, `print_template_placeholders`, `print_template_computed_vars`, `print_template_mc_va_config`, `print_template_defaults` tables — check the schema-drift warning in [03_Architecture_and_Developer_Guide.md](03_Architecture_and_Developer_Guide.md) before assuming any single migration file is ground truth; verify against your actual local dump.
3. **Environment mode**: `admin/index.php` defaults `ENVIRONMENT` to `'production'` unless a `CI_ENV` server variable is set — set `CI_ENV=development` in your local Apache/XAMPP vhost if you want CodeIgniter's verbose error pages instead of silent failures (a blank white screen on error is the default local symptom otherwise).
4. **No menu entry exists** for this module (see [09_Limitations_and_Known_Issues.md](09_Limitations_and_Known_Issues.md)) — you can't click your way to it from the admin sidebar. Navigate directly to `http://localhost/etail_development_src/admin/index.php/print-templates` (adjust for your local path) after logging in.
5. **No special CDN/asset build step** — V2's Konva.js, V1's GrapesJS, Google Fonts, and Font Awesome are all loaded from public CDNs directly in the view files; there's no bundler/webpack step for this module's JS.

## How to test changes

- **PHP syntax**: `php -l <file>` (or the XAMPP binary directly, e.g. `d:\xampp\php\php.exe -l <file>` on Windows) after any controller/model/helper edit — this repo has no automated PHP test suite for this module, so a lint pass plus manual verification is the baseline.
- **Manual verification for a rendering change**: set `ret_settings.template_based = 3` (V2) or `= 1` (V1) via the generic Settings → Retail → Retail Settings screen, ensure an active `'billing'`-code template exists, then print an actual bill (`admin_ret_billing.php::billing_invoice()`) and visually compare against the designer's canvas view.
- **Multi-page regression check**: because pagination is the highest-risk area (see [09_Limitations_and_Known_Issues.md](09_Limitations_and_Known_Issues.md)), test against a bill with enough line items to force a page break, not just a single-page sample — many of the documented past bugs only manifested in multi-page scenarios.
- **Debug aids already built into the renderer**: append `?debug_positions=1` to a Konva-rendered print URL to dump measured element positions via injected JS; append `?konva_pagedebug=1` to get a JSON pagination-decision blob embedded as an HTML comment in the output (`KONVA_PAGEDEBUG_START`/`_END` markers in `konva_receipt_helper.php`).
- **Preview without printing**: the designer's own Preview action (`preview_live()`/`preview_live_v2()`) renders with sample data without needing a real bill — the fastest iteration loop for pure layout work. Note `preview_live_v2()` returns raw HTML directly while the V1 `preview_live()` wraps its response in JSON — don't assume the two have the same response contract if you're scripting against them.

## Common pitfalls when fixing bugs or adding features here

1. **Don't try to "fix" a save by updating the row in place.** Every save is an insert-new-version-and-deactivate-old operation by design (see [06_Update_Rules.md](06_Update_Rules.md)). If you're debugging "my change didn't take effect," check whether a *new* row was created and activated, not whether the row you're looking at changed.
2. **Changing a table-height/positioning constant in `konva_receipt_helper.php`? Check both the pre-calc pass and the render pass.** The file has multiple explicit "these two must match exactly or output drifts" warnings (`_konva_get_table_layout_metrics()` vs `_konva_render_table()`, the shared `_konva_build_table_chunks()` used by both Pass 1.5 and Pass 2). Editing one copy without the other reproduces a bug this file's comments say already happened once.
3. **Adding a new canvas element type in `konva-designer.js`? You must also handle it in `_konva_render_node()` in `konva_receipt_helper.php`.** These are two separate implementations (see the dual-engine drift risk) — a new element type that only exists client-side will render as nothing (or fall through unexpectedly) at print time.
4. **Don't assume `template_based` values `1` and `3` are additive/overlapping** — the code checks `== 3` first and always `exit`s inside that branch, so despite the `if ($template_based == 1 || $template_based == 3)` condition immediately after, that second branch is only ever live for `== 1` in practice.
5. **`'billing'`-group V2 lookups (via `find_konva_template($type, $branch, 'billing')`) do not fall back to global/category templates by design** — if you're debugging "why does this show a not-configured page instead of falling back," that's intentional (see the explicit design-principle comment in `konva_template_not_configured_page()`'s docblock), not a bug to silently patch around.
6. **Don't trust `Documentation/Print_design/*.md`'s description of the V1 editor as "GrapesJS-powered" without checking current code first.** As of this documentation pass, GrapesJS is only loaded inside V1's "Block Designer" sub-modal for authoring individual block HTML — the primary V1 editing surface is a custom block/section stack, not a full-page GrapesJS canvas. That older doc set may describe an earlier iteration; verify against `admin_print_template.php` and `designer.php` directly before relying on it.
7. **There is no permission check to lean on.** If a feature request implies "only managers should be able to delete templates" or similar, that access-control layer does not exist yet anywhere in this module — you'd be building it from scratch, not toggling an existing flag. Don't assume the UI-only delete-button-hiding logic is a real authorization boundary.
8. **Watch for orphaned `print_template_computed_vars` rows** if you're writing any cleanup/migration tooling — deleting a template does not cascade to its computed variables.
9. **When adding a new placeholder, start in `tpl_map_billing_data_to_template()` in `template_receipt_helper.php`**, not `print_template_model.php` — the model's placeholder registry (`get_placeholders_v2()`, `_get_dynamic_fields_v2()`) is downstream of this function's output (via `get_sample_data()`); adding a DB row to `print_template_placeholders` without also populating the value in the mapper gets you a labeled-but-always-empty field.
10. **Check which mapper generation you're touching** (`receipt_helper.php`'s legacy `map_*_data_to_template()` vs `template_receipt_helper.php`'s `tpl_map_*_data_to_template()`) — both are live for different document types (see [09_Limitations_and_Known_Issues.md](09_Limitations_and_Known_Issues.md), item 18), and it's easy to edit the wrong one for a given print flow.
