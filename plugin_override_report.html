Plugin/Override Architecture for Multi-Client ERP

Eliminating sync conflicts, reducing deployment time by 90%, and creating a scalable foundation for client growth.

Prepared by: Engineering Team
Date: 2 March 2026
For: Logimax Technologies

1 Executive Summary

We currently maintain separate Git repositories per client. Every time we update the source code, we manually sync changes to each client — often causing merge conflicts, delayed deployments, and duplicate debugging effort.

✅ Key Outcome
Source updates that currently take 2–4 hours per client (with conflict resolution) will take under 5 minutes — a simple git pull with zero conflicts.
🛡️ Risk Level: Near Zero — We add ~90 lines of new code. We don't remove or rewrite anything existing. If the override system is unused, the application behaves identically.

3 The Proposed Solution

Core Principle

💡
Never modify a core file for a single client. Instead, create an override in a separate directory. The core code stays identical across all clients. Client-specific behavior lives in client_overrides/ — a directory the source repo never touches.

4 Real Example: Making Charge Customization

Scenario: Most clients calculate making charges per gram (source default). But Vetri Jewels calculates making charges per piece with different rates for rings, chains, and bangles.

❌ Current Approach — Fork & Modify Source File

What we do today: Open Vetri's ret_billing.js (1.4 MB), find the function, modify it directly in the core file.

Source version (default):

JavaScript function calculateMakingCharge() {
  var weight = parseFloat($("#gold_weight").val()) || 0;
  var rate = parseFloat($("#mc_rate").val()) || 0;
  return (weight * rate).toFixed(2); // per gram
}

Vetri's modified version (same file, different code):

JavaScript — Modified function calculateMakingCharge() {
  var type = $("#item_type").val();
  var rates = {ring: 800, chain: 1200, bangle: 1500};
  return (rates[type] || 1000).toFixed(2); // per piece
}
💥
Problem: When source updates ret_billing.js (any function — even unrelated ones), Git sees the entire 1.4 MB file as modified on both sides → merge conflict. Developer spends 1–2 hours manually resolving.
✅ New Approach — Override File (12 lines, separate file)

Step 1: Vetri's ret_billing.js is reverted to match source exactly.
Step 2: Create one small override file:

client_overrides/assets/js/admin_ret_billing_override.js

JavaScript — Override // Vetri Jewels: Making charge is per-piece, not per-gram
var _original = calculateMakingCharge;

calculateMakingCharge = function() {
  var type = $("#item_type").val();
  var rates = {ring: 800, chain: 1200, bangle: 1500};
  return (rates[type] || 1000).toFixed(2);
};
✅
Result: Source updates ret_billing.js → Vetri does git pull → zero conflicts. The override file loads after the core file and replaces only the specific function. All other billing functions get the source update automatically.

10 Frequently Asked Questions

Does this require rewriting the entire codebase?
No. We add ~90 lines of framework code. Existing code works as-is. Client customizations are migrated into override files gradually — one module at a time.
What if a change can't be done with an override?
Rare, but possible. We use feature flags — an if/else in source controlled by client_config.php. Still better than forking because the change is in one place, not duplicated per client.
Will this slow down the application?
No measurable impact. The overhead is one file_exists() check per view load (~0.1ms). For JS, the override file loads as an extra script — identical to how we already load multiple scripts.
Can we roll this out gradually?
Yes — that's the recommended approach. Start with one client, one module. Prove it works. Expand to other modules and clients over weeks.
What happens to the DevOps Sync Tool?
It becomes simpler. Instead of cherry-pick vs full-merge decisions, it's always a clean full merge. The divergence analysis tab will show 0% divergence for migrated clients.
What if we add more clients in the future?
New client onboarding becomes: fork source (100% identical) + create client_config.php + add overrides only for what's different. No core file modifications = no future sync pain.
