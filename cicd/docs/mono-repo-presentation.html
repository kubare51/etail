The Problem

What we had — separate repos per client

📦

Duplicate Repositories

  • Each client = separate Git repo
  • Same codebase copy-pasted across 10+ repos
  • Bug fix in one? Manually copy to all others
  • 20 repos × same fix = 20 PRs
⏱️

Slow Onboarding

  • New client = fork repo, reconfigure everything
  • Set up CI/CD from scratch each time
  • ~1 full day per client
🔀

Drift & Inconsistency

  • Client repos diverge over time
  • No way to know which client has which version
  • Merge conflicts when syncing changes
  • Some clients miss critical security patches
🧪

Testing Blind Spots

  • Fix tested on one client, breaks another
  • No unified test across all clients
  • Client-specific bugs surface in production
Logimax Technologies

The Solution: Mono-Repo

One repo, all clients — with a three-layer override system

How It Works

All clients share the same core code. Client-specific differences are handled through overrides — only the files that differ are stored per client.

  • Core code lives in one place — fix once, deploy everywhere
  • Client overrides are scoped — only custom views, CSS, configs
  • Dynamic loader checks client folder first, falls back to core
  • Zero changes to core code per client

Three-Layer Override

Layer 3 Client Override
Highest Priority

clients/ashoka/views/billing.php — Custom billing, logo, GST format

Layer 2 Feature Pack
Shared Extensions

feature_packs/jewellery/ — Industry-specific modules (hallmark, karat)

Layer 1 Core
Base Platform

admin/application/views/ — Standard ERP: billing, inventory, reports

Every task gets its own branch from support. Named with Zoho task ID for traceability.

Pull Request Review

  • PR: feature/* → support
  • Reviewer assigned (TL / senior)
  • Code review + feedback
  • CI checks run automatically
  • No direct pushes to support
🚀

Release Flow

  • QA verifies on staging
  • support → Production merge
  • Auto-deploys to all clients
  • Zero-downtime symlink swap
  • Instant rollback if needed

Branch Naming Convention

Format: <type>/<task-id>-<short-description> — lowercase, hyphens only

📏 Naming Rules

  • Lowercase only — no capitals
  • Hyphens - only — no spaces, no underscores
  • Summarize task into 5–7 meaningful words
  • Remove filler words (and, the, of, for, to)
  • Keep domain abbreviations (grn, sku, gst)
  • Prefix with branch type + Zoho task ID

📝 Example

Type:        feature
Task ID:     124744000005628318
Description: "Add validation for GST calculation
              in invoice module"

→ Result:
feature/5628318-gst-validation-invoice-module

Feature Branch — Day to Day

The exact commands and workflow developers follow

1️⃣ Start a Task

# Get latest from staging
git checkout support
git pull origin support

# Create feature branch
git checkout -b feature/5628318-add-hallmark-field

2️⃣ Develop & Commit

# Make changes, commit with clear messages
git add .
git commit -m "Add hallmark purity field to billing"

# Push feature branch
git push origin feature/5628318-add-hallmark-field

3️⃣ Create Pull Request

  • Open PR: feature/* → support
  • Add description of what changed and why
  • Assign reviewer (TL / senior dev)
  • Link Zoho task ID in PR description
  • CI pipeline runs automatic checks

4️⃣ Review → Merge → Deploy

  • Reviewer reads diff, leaves comments
  • Developer addresses feedback, pushes fixes
  • Reviewer approves → Squash & Merge
  • Auto-deploys to staging for QA testing
  • Delete feature branch after merge
  • After QA → merge support to Production
