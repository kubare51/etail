## 🐛 Troubleshooting

**Check:**
1. Gmail App Password is correct (no spaces)
2. `company` table has SMTP settings
3. Check `admin/email_log.txt` for errors
4. Verify supplier has valid email in database

**Common Errors:**
- "10061 Connection refused" → Wrong SMTP host/port

- "Branch ID not found" → Session issue (fixed in code)

**Check:**

Existing System:
----------------
**Problem Description:**
When printing cheques for supplier/karigar payments, the account number field was displaying incorrect or missing information:

1. **Incorrect Account Numbers**: The system was fetching account numbers from the `bank` table instead of the `ret_karigar` table, resulting in the company's bank account number being displayed instead of the supplier's account number.

2. **Missing Account Numbers**: In cases where the bank table didn't have matching records, the account number field would be empty or display asterisk (*) symbols.

3. **Content Overlapping**: Due to unexpected data or formatting issues, the cheque content would sometimes overlap, making it difficult to read.

**User Impact:**
- Users had to manually write account numbers on printed cheques
- Risk of writing incorrect account numbers
- Unprofessional appearance of cheques
- Time wasted in manual data entry
- Potential payment errors due to wrong account numbers

**Technical Root Cause:**
The SQL query in the `get_po_paid_payment()` function was fetching `acc_number` from the `bank` table (`b.acc_number`) which contains the company's bank account details, not the supplier/karigar's account number. The correct source should be the `ret_karigar` table.


Fix/Enhancement Details:
------------------------
**What Was Fixed:**
Modified the SQL query in the `get_po_paid_payment()` model function to fetch the account number from the correct table (`ret_karigar`) instead of the `bank` table.

**How the System Behaves Now:**
1. **Correct Account Numbers**: Cheques now display the supplier/karigar's account number from the `ret_karigar` table
2. **Graceful NULL Handling**: If a karigar doesn't have an account number, the field displays blank (no errors or asterisks)
3. **No Content Overlapping**: Proper data source ensures consistent formatting
4. **Seamless User Experience**: No changes to user workflow - account numbers automatically populate from karigar master data

**Expected Outcome:**

 RELEASE NOTES — v0.0.1
 Credit Issued Report Fix
 Date: 2026-03-14
 Module: Reports (Credit Issued)
 Developer: Rudra (@dev-rudra-619)

SUMMARY
-------
Fixed two calculation bugs in the Credit Issued Report 
(admin_ret_reports/credit_issued/list) affecting both "Issued" and "Received" 
report types.

Bug ID:       RPT-CLT03
Severity:     P0 (Financial miscalculation)
Track:        A (System/Architecture)
Category:     Logic
GitHub Issue: #1244 (Closed)
Pattern:      PAT-LOGIC-002 (Return-Omission in Debt Calculation)


BUG A — RECEIVED: Received Amount Not Including Discount
--------------------------------------------------------

Problem:
  When Report Type = "Received", the Received Amount column was not including 
  the discount amount (credit_disc_amt). Only tot_amt_received + old_metal_amount 
  was being summed.

Root Cause:
  File: admin/application/models/ret_reports_model.php
  Function: getcreditBill() — report_type=2 branch
  
  1. The SQL query at line 2093 did NOT select credit_disc_amt from ret_billing.
  2. The PHP calculation at line 2110 only added old_metal_amount:
     $items['tot_amt_received'] = $items['tot_amt_received'] + $old_metal_amount;

Fix Applied:
  1. Added IFNULL(b.credit_disc_amt,0) as credit_disc_amt to the SQL SELECT
  2. Updated the PHP sum to include credit_disc_amt:
     $items['tot_amt_received'] = $items['tot_amt_received'] + $old_metal_amount 
                                  + $items['credit_disc_amt'];


BUG B — ISSUED: Balance Amount Showing Incorrectly (0.00)
---------------------------------------------------------

Problem:
  When Report Type = "Issued", the Balance Amount column was showing 0.00 
  for all rows instead of the correct outstanding balance.

Root Cause:
  File: admin/application/models/ret_reports_model.php
  Function: getcreditBill() — report_type=1 branch
  
  The due_amt SQL formula at line 2056 was WRONG:
    BEFORE: (b.tot_amt_received - IFNULL(ret.credit_ret_amt,0)) as due_amt
  
  This calculates "paid minus returns" — which is NOT the balance.
  The correct formula should be "bill total minus paid minus returns".

Fix Applied:
    AFTER:  (b.tot_bill_amount - b.tot_amt_received - IFNULL(ret.credit_ret_amt,0)) as due_amt


FILES CHANGED
-------------
  1. admin/application/models/ret_reports_model.php
     - Line 2056: Corrected due_amt formula (Bug B)
     - Line 2093-2095: Added credit_disc_amt to SQL SELECT (Bug A)
     - Line 2110: Added credit_disc_amt to PHP sum (Bug A)
