## Primary Tables (Written by this Module)

### 1. `customer`
**Role in module**: Source of truth for customer identity, auth, and status.

| Column | Used As | Access | Notes |
|---|---|---|---|
| `id_customer` | PK | R/W | Core FK across all tables |
| `mobile` | Login credential, FK | R | No unique index confirmed — potential duplicates |
| `passwd` | Auth | R/W | ⚠️ `base64_encode(plain)` — NOT a hash |
| `active` | Gate for login | R | `active=1` = allowed. `active=0` = blocks login |
| `kyc_status` | KYC gate (client-side) | R/W | 'APPROVED'/'PENDING'/'REJECTED' |
| `pin_no` | MPIN | R/W | For `is_pin_required` flow |
| `last_generated_otp` | OTP verification | R/W | 6-digit OTP stored as plain text |
| `last_otp_expiry` | OTP expiry | R/W | Datetime string |
| `id_branch` | Branch assignment | R | Used for branchwise rate/gateway lookup |
| `notification` | FCM push enabled | R/W | 1=enabled |
| `aadhar_ImgName` | KYC Aadhaar image path | W | Stored on disk, path in DB |
| `is_new` | First login flag | R/W | `1` = new (first time login), `0` = returning |
| `added_by` | Source of registration | W | `2` = Customer mobile app |

### 2. `scheme_account`
**Role**: Customer's enrolled scheme accounts — core of the chit system.

| Column | Used As | Access | Notes |
|---|---|---|---|
| `id_scheme_account` | PK | R/W | FK in `payment`, `wallet_transaction` |
| `id_customer` | FK → customer | R | Foreign key — no cascade observed |
| `id_scheme` | FK → scheme | R | Determines scheme type, rules |
| `scheme_acc_number` | Display account number | R/W | Generated by `account_number_generator()` |
| `active` | Account status | R | `1`=active, `2`=pending approval, `0`=inactive |
| `is_closed` | Scheme completion | R | `1` = closed/completed |
| `paid_installments` | Installment count | R/W | ⚠️ Updated incorrectly can break due calc |
| `disable_payment` | Block payment | R | Admin flag to prevent app payments |
| `id_branch` | Branch for this account | R | Used for gateway, rate selection |
| `referal_code` | Referral code used | W | Stored on join |
| `added_by` | Origin | W | `2`=mobile app, `3`=admin mobile |
| `is_opening` | Opening balance | R | `1` = pre-existing account migrated |
| `firstPayment_amt` | Lock first payment amount | R | For flexible scheme first-pay rules |
| `group_code` | Lucky draw group | R/W | Updated by `updateGroupCode` in payment |

### 3. `payment`
**Role**: Every payment transaction — pending, success, failed.

| Column | Used As | Access | Notes |
|---|---|---|---|
| `id_payment` | PK | R/W | Referenced in `payment_referral`, `employee_incentive` |
| `id_scheme_account` | FK → scheme_account | R | Core payment → account link |
| `payment_status` | State machine | R/W | `7`=pending, `2`=await, `1`=success, `3`=fail, `4`=cancel |
| `payment_amount` | Money | R/W | Float — no currency normalization |
| `metal_weight` | Weight (grams) | R/W | For weight-scheme payments |
| `receipt_no` | Receipt | W | Generated by `get_receipt_no()` after success |
| `id_transaction` | Gateway ref | R/W | txnid from gateway |
| `added_by` | Origin | W | `2`=customer mobile |
| `due_type` | Due classification | W | `ND`, `PD`, `AD`, `PN`, `AN` |
| `no_of_dues` | Number of installments | R/W | Multi-due payment |
| `date_payment` | Payment date | W | Used for installment month detection |
| `payment_mode` | Mode | W | CC, NB, CD, CO, OP, etc. |

> ⚠️ **CRITICAL BUG RISK**: `payment_status` transitions are NOT validated. A row can go from `status=7` (pending) to `status=1` (success) AND then be updated again by a duplicate webhook to `status=1` again. No guard against duplicate callback processing.

### 4. `wallet_transaction`
**Role**: Wallet credit/debit records.

| Column | Used As | Access | Notes |
|---|---|---|---|
| `id_wallet_transaction` | PK | R | Pagination cursor for wallet history |
| `id_wallet_account` | FK → wallet_account | R | Links to customer |
| `transaction_type` | Direction | W | `0`=credit, `1`=debit |
| `value` | Amount | W | The wallet credit/debit amount |
| `description` | Label | W | "Payment redemption", etc. |
| `id_sch_ac` | Linked scheme account | W | Nullable — may be null for non-scheme transactions |

### 5. `kyc`
**Role**: Customer KYC documents.

| Column | Used As | Access | Notes |
|---|---|---|---|
| `id_kyc` | PK | R | — |
| `id_customer` | FK | R/W | — |
| `kyc_type` | Document type | R/W | `1`=Aadhaar, `2`=PAN |
| `number` | Document number | R/W | e.g., PAN number |
| `status` | Verification status | R | Admin-set |

## Index Analysis

| Table | Column | Index Type | Risk |
|---|---|---|---|
| `customer` | `mobile` | UNKNOWN — should be UNIQUE | 🔴 High — If not unique, duplicate mobile could exist |
| `scheme_account` | `id_customer` | UNKNOWN — should be INDEX | 🟡 MED — `where id_customer=?` on large tables is slow without index |
| `payment` | `id_scheme_account` | UNKNOWN — should be INDEX | 🔴 High — `get_schemeaccount_detail` joins payment multiple times |
| `payment` | `payment_status` | UNKNOWN | 🟡 MED — `where payment_status=7` slow for cleanup |
| `payment` | `date_payment` | UNKNOWN | 🟡 MED — Installment month calculations use `DATE_FORMAT()` on this column |
| `wallet_transaction` | `id_wallet_account` | UNKNOWN | 🟡 MED — Balance aggregation uses this |
| `metal_rates` | `id_metalrates` | PRIMARY | ✅ OK — used in `ORDER BY id_metalrates DESC LIMIT 1` |

> ⚠️ **Note**: `DATE_FORMAT(p.date_payment, '%Y%m')` in payment join prevents index use. Full table scan risk on large `payment` tables.
