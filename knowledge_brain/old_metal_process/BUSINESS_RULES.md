# Business Rules — Old Metal Process Module

## BR-1: Pocket Eligibility
- Items eligible for pocketing must have `is_transferred=1` in `ret_bill_old_metal_sale_details`
- Tagged items must have `tag_status=6` (sold/returned) and `tag_process=0` or `tag_process=2`
- Partly-sold items must have `is_partial_sale=1` with positive remaining `gross_wt` (HAVING clause)
- Opening stock items use `smith_company_op_balance` instead of billing tables
- An item can only be in one pocket: `pocket.tag_id IS NULL` / `old_pocket.old_metal_sale_id IS NULL` guards prevent duplication
- Pocket `status=0` means OPEN; `status=1` means CLOSED (but system never sets it to 1 — OMP-007)

## BR-2: Melting Issue Rules
- Only pockets with `status=0` and `piece>0` are eligible
- Partial issue allowed: `issue_nwt < net_wt` (HAVING clause in model)
- Per pocket, issued quantities tracked separately by metal type (id_metal_type)
- Combined polishing + melting issue totals tracked: `(polishing_issue + melting_issue) = total_issue`
- Non-tagged items and tagged items use separate sub-total fields in form

## BR-3: Melting Status State Machine
```
melting_status == 0 → Melting Issued
melting_status == 1 → Melting Received
melting_status == 2 → Testing Issued
melting_status == 3 → Testing Received
melting_status == 4 → Refining Issued
melting_status == 5 → Refining Received (implied by refining_status=1)
```
- Transitions are sequential; processes should only read records at their expected state
- System does NOT enforce prior state before advancing (OMP-008)

## BR-4: Category Classification at Receipt
- At melting/testing/polishing receipt, items are classified into category + section + product + design + sub_design
- This classification determines which lot + stock inventory is updated
- `is_non_tag=1` → updates `ret_nontag_item` stock
- `is_non_tag=0` → creates a lot inward but no direct nontag update (goes through separate lot system)

## BR-5: GST Tax Split Rule
```
Same state → CGST split: receipt_charges × perc / 2 each for CGST and SGST
Different state → IGST: receipt_charges × perc
```
- Applies only to Refining Receipt (has charges with tax)
- Determined by comparing karigar state vs company state
- ⚠️ OMP-002: company state lookup uses wrong field

## BR-6: Stock Upsert Logic (Non-Tag Items)
```
IF item exists (same section + product + design + sub_design + branch):
    UPDATE ret_nontag_item: +gross_wt, +net_wt, +no_of_piece
ELSE:
    INSERT ret_nontag_item (new row)
ALWAYS:
    INSERT ret_nontag_item_log (movement record)
    INSERT ret_section_nontag_item_log (section-level movement)
```
This pattern runs for: Melting Receipt, Testing Receipt, Refining Receipt, Polishing Receipt

## BR-7: Lot Inward Classification
- Each lot record in `ret_lot_inwards` has `lot_from` identifying its source:
  - `lot_from=2`: From Melting
  - `lot_from=4`: From Testing
  - `lot_from=5`: From Polishing
- Lot type is always 1 (standard)
- Lot narration for Polishing: 'From Polishing Process'

## BR-8: Process Number Format
- Generated by `generate_process_number($process_for, $id_metal_process)`
- Format varies by process type and for/receipt: prefix + sequential number (zero-padded)
- Race condition risk (OMP-005): two concurrent saves can get same number

## BR-9: Diamond/Stone Weight Tracking
- `dia_wt` (diamond weight) is tracked separately from `gross_wt` and `net_wt` in pockets
- Carried through issue records as `issue_diawt`
- Diamond weight is tracked from `ret_taging_stone` (stone_type=1 = diamond)
- In partly-sold calculations, diamond weight is net of re-tagged (stock process) adjustments

## BR-10: Against-Melting Receipt Flow (Testing)
- When Testing Receipt 'Against Melting' is YES:
  - UI shows `#against_melting_receipt` table instead of standard `#testing_receipt`
  - Operator can choose: "Add to Next Process" or "Add to Stock"
  - Different save flow in controller for `process_type=1` vs `process_type=2`
  - This path is partially implemented (the table exists in form.php but the JS handling is present)

## BR-11: Opening Stock Pocket
- `is_against_opening=1` flag on pocket enables using `smith_company_op_balance` as stock source
- Uses `get_opening_metal_stock_list()` endpoint instead of bill-based stock list
- Opening balance items tracked with their category and net weight

## BR-12: Polishing vs Melting Mutual Exclusion
- Items in a pocket can go to EITHER polishing OR melting — not both simultaneously
- The `get_melting_pocket_details()` query sums both `melting_issue_nwt` + `polishing_issue_nwt` to compute total issued
- HAVING `issue_nwt < net_wt` prevents showing fully-issued pockets

## BR-13: Karigar Binding
- For Issue transactions: karigar is required
- For Receipt transactions with "Against Melting = Yes" (Testing): karigar is NOT required (receipt comes back directly)
- For all other receipts: karigar is required
- JS validation: `id_karigar==null && (process_for==1 || (process_for==2 && against_melting!=2))` → blocks submit
